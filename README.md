## 🏛 I. Философия: Приложение как Единая Живая Книга

**Code as Book (CoB)** — это архитектурная парадигма для современных бизнес-приложений (в первую очередь Android). Она отрицает навязанную сложность классических архитектур (Clean, Hexagonal, MVVM) с их горизонтальным слоением и «божественными» ViewModel.

В CoB одно приложение — это **Книга**. Это автономный, самодостаточный мир, который собирается в один APK/AAB.

### Главные принципы:

*    **Смерть «Архитектурного Налога»**: Логика собрана вертикально. Внутри Главы есть свои Правила, свои Экраны и свои Данные.
*   ✍️ **Читаемость — приоритет №1**: Структура прозрачна, как оглавление. Навигация — это читаемый `when`.
*   🚫 **Смерть ViewModel и «Умного UI»**: UI — тупой рендерер. Он просто читает данные из дата-класса (`LocalState`) и отрисовывает их.
*   👷♂️ **Блоки Правил — одноразовые рабочие (Fire-and-Forget)**: **Блок Правил** получает Письмо, выполняет свою линейную цепочку атомарных правил, отправляет результат (или следующее Письмо) — и умирает.
*   🕰 **Состояние — живая сущность с TTL**: Дата-класс (`State`) не привязан к жизни UI. Он живет автономно и имеет встроенный таймер самоуничтожения.
*   🧠 **Нервная система**: Все компоненты общаются исключительно через **Письма (Letters)** и **Шину (PlotBus)**.

##  II. Анатомия Книги

Каждая Книга состоит из трех глобальных частей: **Введение**, **Главы** и **Адаптер**.

### Физическая структура проекта

```text
/Book (Корень приложения)
 ├── /Introduction (Введение — техническая обвязка)
 │    ├── /Core (PlotBus, Навигатор на when, Контекст)
 │    ├── /Entities (Общие сущности книги)
 │    └── /Screens (Все общие экраны приложения)
 │         └── /Errors (Экраны ошибок для Менеджера Ошибок)
 │
 ├── /Chapter_Auth (Глава 1 — например, Авторизация)
 │    ├── /Rules (Блоки правил этой главы)
 │    ├── /Screens (Экраны, принадлежащие только этой главе)
 │    └── /State (LocalState для этой главы)
 │
 ├── /Chapter_BackgroundSync (Глава 2 — работает без экрана)
 │    └── /Rules (Только блоки правил)
 │
 └── /Legacy_Bridge (Адаптер для старого кода или внешних SDK)

### Компоненты

#### 1. Введение (Introduction / Physics)

Фундамент Книги. Не содержит бизнес-логики конкретных фич.

*   **Ядро (Core):**
    *   `PlotBus` — локальная шина событий
    *   `Navigator` — глобальный синглтон навигации на основе `when`
    *   `Context` — контекст приложения

*   **Сущности (Entities):**
    Общие структуры данных, используемые во всей Книге (DTO, модели ответов).

*   **Экраны (Screens):**
    Единое хранилище всех UI-компонентов приложения.
    Внутри лежит подпапка `/Errors`, где хранятся системные экраны для Менеджера Ошибок (например, «Нет сети», «Критический сбой»).

#### 2. Глава (Chapter)

Глава — это автономный сценарий (фича). По своей сути, Глава — это тоже `when`. Это реактивный маршрутизатор, который слушает Шину (`PlotBus`) и реагирует на входящие Письма.

*   **Изоляция:** Главы не зависят друг от друга.
*   **Без состояния:** Глава не хранит внутри себя UI и не хранит данные (дата-классы). Она абсолютно «чистая» — только логика и реакции на события.
*   **Без экрана (фон):** Глава может работать вообще без UI (например, фоновая служба), но её механика остается той же.
#### 3. Блок Правил (Rules Block)

Набор атомарных правил, выполняемых строго линейно.

*   **Конвейер:** Правила выполняются друг за другом.
*   **Бинарный исход:** Каждое правило возвращает `True` или `False`.
*   **Асинхронность:** Блок выполняется асинхронно относительно UI, но синхронно внутри себя.
*   **Одноразовость:** Запустился → выполнился → умер.

#### 4. Адаптер (Legacy Bridge)

Шлюз для интеграции старого кода или внешних SDK. Изолирует «грязь» легаси от чистой структуры Книги.

##  III. Нервная Система: Шина и Письма
Все компоненты общаются исключительно через **Письма (Letters)**, которые доставляет **Шина (PlotBus)**. Прямых вызовов нет.

### 1. Анатомия Письма

Строго типизированный объект:

*   `SENDER`: Адрес отправителя.
*   `RECIPIENT`: Адрес получателя.
*   `METHOD`: Имя метода, который должен выполнить получатель.
*   `DATA`: Параметры для метода (`Map` или DTO).

### 2. Шина (PlotBus) и Реестр (Registry)

Шина работает как курьер:

1.  Извлекает из Письма поле `RECIPIENT`.
2.  Спрашивает у Реестра: «Существует ли объект с таким адресом?».
3.  Если объект жив — Реестр дает ссылку. Если мертв (по TTL) — создает новый.
4.  Шина передает Письмо получателю.
### 3. Логгер (Наблюдаемость)

Шина ведет последовательный лог всех писем (время, отправитель, получатель, метод, статус). Разработчик читает хронологию в логах, как сюжет книги.

### 4. Адресация

Префикс с именем книги опускается. Формат: `Сущность.Метод` (например, `CHAPTER_AUTH.LOGIN`, `STATE_USER.UPDATE`).

## 🎬 IV. Логика Сюжета: Реактивная Глава

Глава — это автономный сценарий. Это `when`, который слушает Шину.

### Правила общения (Инкапсуляция)

*   **Блоки Правил** общаются только со своей Главой.
*   Они шлют Главе **ТОЛЬКО** сигнал `SUCCESS`.
*   При ошибке Блок умирает, а ошибка уходит в Менеджер Ошибок.

### Смена сцен (Навигация)

*   Глава не вызывает Навигатор напрямую.
*   Глава запускает **Блок Правил**, который дергает Навигатор.
*   Как только новый экран отрисован, управление переходит к новой Главе. Предыдущая Глава завершает работу.

### Закон Успеха

*   Глава реагирует только на `SUCCESS` от своего Блока Правил.
*   Пришел `SUCCESS`? → Глава решает, что делать дальше (новый Блок или конец).
*   Глава не держит состояние и не ждет. Если понадобится снова — Реестр создаст её заново.
## ⚠️ V. Физика Действия: Обработка Ошибок

Двухуровневая обработка ошибок:

### 1. Легкая (Бизнес) ошибка

*   **Пример:** неверный email, пустое поле.
*   **Кто обрабатывает:** Само Правило внутри Блока.
*   **Механизм:** Правило возвращает `False` (или `True` для инверсного). Цепочка прерывается. Правило обновляет `LocalState` (подсветка поля) или показывает Toast. Глава об этом не узнает.

### 2. Тяжелая (Рантайм) ошибка

*   **Пример:** нет интернета, ошибка БД, NPE.
*   **Кто обрабатывает:** Менеджер Ошибок (через `try/catch` Блока).
*   **Механизм:** Ошибка перехватывается `catch`. Отправляется Письмо `CRITICAL_ERROR` в Менеджер Ошибок. Менеджер решает, какой экран показать.

## ⚙️ VI. Механизмы Исполнения (CoB Engine)

### 1. Short Circuit (Короткий путь данных)

Оптимизация внутри одной Главы. Правило может обновить `LocalState` напрямую, не посылая Письмо обратно в Главу. Экран перерисовывается мгновенно. Глава получает сигнал `SUCCESS` только по завершении всего Блока.

### 2. Изоляция и Жизненный Цикл Состояния (No Shared State + TTL)

*   У каждой Главы свой `LocalState` (дата-класс).
*   **TTL (Time To Live):** State не привязан к UI. Когда таймер истекает, State самоуничтожается.
*   **Сохранение:** Перед смертью State может записать важные данные в кэш (DataStore/DB).
*   **Восстановление:** При новом запросе Шина создаст новый State и подтянет данные из кэша, если они есть.
## ✅ Выгоды и ⚠️ Ограничения CoB 2.0

Как и любая архитектурная парадигма, CoB 2.0 имеет свои сильные стороны и компромиссы. Ниже — объективный анализ для команд, рассматривающих внедрение.

### ✅ Преимущества

| Преимущество | Описание |
|--------------|----------|
| **Читаемость как книга** | Структура проекта = оглавление. Новый разработчик понимает поток за 5 минут. |
| **Нет ViewModel-хаоса** | UI тупой, состояние автономно, нет «божественных объектов», держащих всё. |
| **Вертикальная инкапсуляция** | Фича полностью внутри Главы: правила, экраны, состояние. Никакого горизонтального размазывания. |
| **Автоматическая сборка мусора** | TTL + самоуничтожение состояний → меньше утечек памяти, проще управлять жизненным циклом. |
| **Логирование как сюжет** | Шина логирует каждое письмо → отладка превращается в чтение хронологии событий, а не поиск по стектрейсу. |
| **Идеально для сценариев** | Авторизация, онбординг, формы, фоновые задачи — всё это естественные «главы» книги. |
| **Легкая интеграция легаси** | Legacy Bridge изолирует старый код, не загрязняя основную архитектуру. |

### ⚠️ Ограничения и риски

| Ограничение | Почему это важно | Для каких приложений критично |
|-------------|------------------|-------------------------------|
| **Шина работает синхронно внутри приложения** | Хотя блок выполняется в корутине (не блокирует UI), сами правила идут строго последовательно. Это хорошо для линейных сценариев, но плохо для параллельных операций (например, загрузка 3 независимых API одновременно). | Приложения с дашбордами, где нужно грузить много данных параллельно; чаты с实时-обновлениями; игры. |
| **Нет реактивного связывания между Главами** | Главы изолированы. Если одной главе нужны данные из другой — только через Письмо + Реестр. 
| **Навигация через Блок Правил** | Нельзя просто вызвать `navigateTo()` из UI. Всё должно проходить через Правила → Навигатор. Это дисциплинирует, но замедляет прототипирование. | MVP-стартапы, где скорость разработки важнее архитектуры. |
| **Кривая обучения** | Парадигма радикально отличается от MVVM/Clean. Команде нужно время на перестройку мышления. | Большие команды с устоявшимися практиками; проекты с высокой текучкой кадров. |

### 🎯 Когда CoB 2.0 идеален?

*   Бизнес-приложения с четкими сценариями: банки, медицина, логистика, CRM.
*   Приложения с формами, шагами, авторизацией, настройками.
*   Проекты, где важна наблюдаемость и отладка (логи = сюжет).
*   Команды, уставшие от переусложненных архитектур и хотят простоты без хаоса.

### 🚫 Когда стоит подумать дважды?

*   Прототипы и MVP, где скорость > архитектура.
*   Команды, не готовые менять мышление с «слои» на «сценарии».

> 💡 **Совет**: Попробуйте CoB 2.0 на одной фиче (например, авторизации). Если команда почувствует облегчение — масштабируйте. Если почувствуете сопротивление — возможно, ваша доменная область требует другой модели.
