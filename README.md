# 📖 Code as Book (CoB) Methodology

> Превращаем разработку ПО из проектирования «заводов-монолитов» в написание живой, читаемой и автономной истории.

**Code as Book (CoB)** — это децентрализованная архитектурная парадигма для современных бизнес-приложений.
Она заменяет горизонтальное слоение классических архитектур (Clean, Hexagonal) на вертикальное деление по смыслу, 
делая структуру проекта такой же прозрачной, как оглавление книги.

---

##  I. Философия: Смерть «Архитектурного Налога»

В классических архитектурах логика размазана горизонтально (`Data -> Domain -> Presentation`). 
Чтобы добавить одну кнопку, разработчик «протыкает» 5–7 слоев, тратя до 40% времени на обслуживание структуры.

**CoB меняет правила игры:**

*   🏛 **Приложение — это Библиотека.** Проект состоит из независимых **Книг** (модулей).
*   📘 **Книга — это автономный мир.** У неё есть своя память (Сущности), свои глаза (Экраны) и своя воля (Главы).
*   Каждая книга содержит собственное ядро инфраструктуры, что позволяет ей быть полностью самодостаточной.
*   ✍️ **Читаемость — приоритет №1.** Если сюжет приложения нельзя прочитать как текст, это плохой код.

---

## 📚 II. Анатомия Книги

Каждая Книга в CoB — это **автономный модуль**. Она не зависит от глобального контекста приложения. Вся необходимая инфраструктура находится внутри неё. Это позволяет легко переносить, дублировать или удалять целые модули без риска нарушить работу остальной системы.

### Ключевые компоненты Книги:

1.  **Глава (Chapter):** Режиссерский сценарий. Точка входа в логику модуля. Содержит реактивный маршрутизатор, который реагирует на события.
2.  **Правила (Rules):** Блоки логики. Делятся на общие для всей книги и специфичные для конкретной главы.
3.  **Введение (Introduction / Physics):** Ресурсы и инфраструктура мира:
    *   **Ядро (Core):** Локальная шина событий (`PlotBus`), навигатор и контекст.
    *   **Сущности (Entities):** Структуры данных, используемые только в этой книге.
    *   **Экраны (Screens):** UI-компоненты вместе со своим состоянием (`State`).
4.  **Адаптер (Legacy Bridge):** Шлюз для интеграции старого кода. Для новой системы он выглядит как обычное Правило, а для старого кода — как привычный сервис.

## 🧠 III. Нервная система: Шина и Письма

Все компоненты общаются исключительно через **Письма (Letters)**, которые доставляет **Шина (PlotBus)**.

### 1. Анатомия Письма
Каждое письмо — это строго типизированный объект, содержащий:
*   **`SENDER`**: Адрес отправителя (кто породил событие).
*   **`RECIPIENT`**: Адрес получателя (кому адресовано).
*   **`METHOD`**: Имя метода, который должен выполнить получатель.
*   **`DATA`**: Параметры для этого метода (`Map<String, Any>` или конкретный DTO).

### 2. Логика работы Шины (PlotBus)
Шина работает по принципу **«Найти или Создать»**:

1.  **Чтение адреса:** Шина получает письмо и извлекает поле `RECIPIENT`.
2.  **Поиск объекта:**
    *   Если объект с таким адресом уже существует в реестре Книги → Шина передает письмо ему.
    *   Если объекта **нет** → Шина **создает новый экземпляр** этого объекта (Главу, Правило или Экран) и сразу передает письмо.
3.  **Исполнение:** Получатель вызывает метод, указанный в поле `METHOD`, передавая туда `DATA`.

> **Преимущество:**
> Это обеспечивает **ленивую загрузку**. Компоненты не занимают память, пока они не нужны.
> Приложение стартует мгновенно, так как создается только то, что требуется прямо сейчас для обработки текущего письма.

### 3. Адресация по полному пути
Для взаимодействия между разными Книгами используется строгая система именования, исключающая конфликты:
`BOOK_NAME.SCREEN_NAME.WIDGET_ID` или `BOOK_NAME.METHOD_NAME`

**Примеры:**
*   `AUTH_BOOK.LOGIN_SCREEN.BUTTON_SUBMIT`
*   `PROFILE_BOOK.METHOD_LOAD_USER_DATA`

## 🎬 IV. Логика Сюжета: Реактивная Глава

Глава — это не процессор, ожидающий отчетов, а **реактивный маршрутизатор успехов**. Её код представляет собой декларативную структуру `when` (или `switch`).

### Закон Успеха (Happy Path)
*   Глава реагирует на письма в которых есть сигнал для Главы
*   Глава реагирует  на сигнал `SUCCESS`.
*   Пришло письмо `LOGIN_SUCCESS`? → Запустить следующий Блок Правил.

Если цепочка прервалась ошибкой, Глава об этом не знает так как к этому времени уже умерла

---

## ️ V. Физика Действия: Автономия Правила

Правило в CoB — это **Атомарный Блок Правил**, последовательная цепочка операций, работающая как единое целое.

### Механика выполнения:
1.  **Строгая последовательность:** Внутри блока правила выполняются друг за другом.
2.  **Бинарная логика:** Каждое правило имеет два исхода:
    *   ✅ **Успех:** Передача управления следующему правилу.
    *   ❌ **Ошибка:** Немедленное прерывание блока -с выводом ошибки на экран или в менеджер ошибок
3.  **Асинхронность:** Весь блок выполняется в отдельном потоке, не блокируя UI.

### Двухуровневая обработка ошибок:

| Тип ошибки | Пример | Кто обрабатывает | Механизм |
| :--- | :--- | :--- | :--- |
| **Легкая** | Неверный email, пустое поле | **Само Правило** | Обновляет `LocalState` экрана или показывает Toast. |
| **Тяжелая** | Нет интернета, ошибка БД | **Менеджер Ошибок** | Отправляет письмо `CRITICAL_ERROR`. Менеджер решает, какой экран показать (ошибка сети, логин). |

## ⚡ VI. Механизмы исполнения (CoB Engine)

### 1. Short Circuit (Короткий путь данных)
Оптимизация внутри одной Книги. Правило обновляет `LocalState` напрямую, минуя Главу.
Экран перерисовывается мгновенно. Глава получает лишь короткий сигнал «УСПЕХ» когда блок правил выполнится полностью.

### 2. Изоляция Состояния (No Shared State)
У каждой Книги свой `GlobalState`. Книги **не имеют** прямого доступа к данным друг друга.
*   **Обмен данными:** Только через Письма (Шину).
*   **Спецсведения:** Если Книге Б нужны данные из Книги А, она отправляет запрос (`REQUEST_TOKEN`) и получает ответ (`TOKEN_RESPONSE`), сохраняя данные у себя локально.

## 📝 Резюме преимуществ

1.  **Автономность:** Любую Книгу можно выдернуть и вставить в другой проект.
2.  **Читаемость:** Код читается как сюжетная линия, а не как лабиринт классов.
3.  **Безопасность:** Ошибки не пробиваются сквозь слои, а гасятся локально или обрабатываются системным Менеджером.
4.  **Масштабируемость:** Новые фичи добавляются как новые Главы, не ломая старые.
5.  **Производительность:** Ленивая загрузка компонентов через Шину экономит ресурсы памяти при старте.
