📖 Манифест методологии «Код как Книга» (CoB)
«Код как Книга» — это децентрализованная архитектурная парадигма, превращающая разработку ПО из проектирования «заводов-монолитов» в написание живой, читаемой и автономной истории.
1. Фундаментальная философия: Смерть «Архитектурного Налога»
В классических архитектурах (Clean, Hexagonal) логика размазана горизонтально (Data -> Domain -> Presentation). Чтобы добавить одну кнопку, разработчик «протыкает» 5–7 слоев, тратя до 40% времени на обслуживание структуры.
CoB заменяет это вертикальным делением:
•
Приложение — это Библиотека. Проект состоит из независимых Книг (модулей).
•
Книга — это автономный мир. Она имеет свою память (Сущности), свои глаза (Экраны) и свою волю (Главы).
•
Читаемость как приоритет. Если сюжет приложения нельзя прочитать как текст, это плохой код.
2. Анатомия Книги (Оглавление)
Каждая Книга имеет строгую структуру папок, диктуемую плагином:
📚 ВВЕДЕНИЕ (Introduction — Физика Мира)
Здесь сосредоточены инструменты, без которых мир не работает:
•
СУЩНОСТИ (Entities): Описание памяти. Переменные здесь привязаны к виджетам через ID.
•
ЭКРАНЫ (Screens): Визуальный ряд на Jetpack Compose.
•
ПРАВИЛА (Rules): Законы физики. Атомарные процедуры (Запрос, Валидация, Установка данных).
•
ПОДКЛЮЧИТЬ (Imports): Реестр внешних библиотек и их шаблонов.
📖 ГЛАВЫ (Chapters — Сюжетные линии)
Логический центр принятия решений. Глава — это Режиссер. Она говорит, что происходит, но не знает, как это устроено технически.
🔗 ЗАМЕТКИ (Adapters — Заметки на полях)
Шлюзы для связи с Legacy-кодом или внешним миром (GPS, Bluetooth, старые API).
3. Нервная система: Шина и Письма
Связь между всеми компонентами происходит через Письма (Letters), доставляемые Шиной (Bus).
Структура Письма (PlotSignal):
1.
ОТПРАВИТЕЛЬ: Кто породил событие (напр. КНИГА.ЭКРАН.КНОПКА).
2.
ПОЛУЧАТЕЛЬ: Кому адресовано (напр. ГЛАВА_АВТОРИЗАЦИЯ или ПРАВИЛО_СЕТЬ).
3.
МЕТОД: Что именно произошло (напр. НАЖАТИЕ или УСПЕХ).
4.
ДАННЫЕ: Карманы с параметрами (JSON/Map).
Принцип Traceability: ID объекта == Имя Класса == Имя Файла. Лог Шины — это готовая стенограмма работы приложения, которую поймет даже бизнес-заказчик.
4. Логика Сюжета: Закон Успеха (Happy Path)
Глава — это «Хроника Побед». В ней запрещены ветвления по ошибкам.
•
Декларативность: Глава состоит только из триггеров: Событие -> Реакция.
•
Слепая Вера: Глава реагирует только на сигнал УСПЕХ от Правила. Если Правило споткнулось, Глава «замирает», не загромождая сюжет техническим мусором (404, Timeout и т.д.).
•
Цепочки: Глава связывает выход одного Правила со входом другого, создавая сюжетную линию.
5. Физика Действия: Автономия Правила
Правило — это Ответственный Исполнитель (Каскадер). Оно берет на себя всю «грязную работу».
Архитектурный Контракт Правила:
Каждое Правило обязано иметь три блока:
1.
ДЕЙСТВИЯ: Линейный конвейер команд (Установить, Запросить, Сохранить).
2.
ОШИБКА (Обязательно): План спасения. Если любая команда конвейера упала, Правило само вызывает обработчик (Тост, Переход на экран ошибки) и не беспокоит Главу.
3.
УСПЕХ (Автоматически): Если конвейер дошел до конца, Шина отправляет письмо в Главу.
Вертикальное деление Правил: Для каждой Главы создается своя подпапка в ПРАВИЛАХ. Это изолирует уникальную логику сюжета от общих законов мира.
6. Механизмы исполнения (Магия CoB)
⚡ Short Circuit (Короткий путь данных)
Данные не гоняются через Главу.
1.
Глава вызывает Правило.
2.
Правило пишет результат напрямую в СОСТОЯНИЕ (State).
3.
Экран (UI) мгновенно перерисовывается, так как он слушает State.
4.
Глава получает лишь короткий отчет: «Готово».
🤖 Транспилятор как Архитектурный Цензор
Плагин физически не дает нарушить методологию:
•
Запрещает писать логику в Экранах.
•
Запрещает писать if/else в Главах.
•
Автоматически генерирует «скелеты» Правил с блоками УСПЕХ/ОШИБКА.
•
Транслитерирует все технические ID, сохраняя стабильность проекта при смене языка (RU/EN/DE).
🔗 Адаптеры (Двусторонние Шлюзы)
Адаптер — это единственный объект, имеющий право касаться «грязного» Android-кода. Он переводит внешние сигналы в Письма и обратно. Книга остается стерильной.
Резюме:
В методологии CoB разработчик перестает быть «механиком», который возится в масле инфраструктуры. Он становится Автором.
•
Пиши Главу как поэт (о смысле).
•
Пиши Правило как юрист (о деталях и рисках).
•
Пусть Книга работает сама.
Этот подход сокращает Time-to-Market в разы, делая поддержку приложения такой же простой, как чтение оглавления.
