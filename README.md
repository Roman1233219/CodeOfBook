# Методология «Код как Книга» (Code of Book)

**«Код как Книга»** — это децентрализованная архитектурная методология, которая превращает разработку ПО из проектирования «многослойных заводов» в написание **живых сюжетов**. 

Данный проект — это манифест и эталонная реализация концепции на Kotlin и Jetpack Compose.

---

## 📖 1. Фундаментальная философия

В классических архитектурах (Clean Architecture, Hexagonal) логика одной функции «размазана» по горизонтальным слоям (Data, Domain, Presentation).
Чтобы добавить одну кнопку, разработчик обязан проткнуть 5-7 слоев, создавая мапперы, интерфейсы и DTO. 
Это порождает **Архитектурный Налог** — потерю до 40% времени на обслуживание структуры, а не на написание бизнес-логики.

**Методология CoB предлагает «вертикальное» деление по смыслу:**

- **Приложение — это Библиотека**. Проект состоит из независимых **Книг** (модулей, например `book_test`, `book_auth`).
  *   Любой файл (Глава, Экран) является автономным аналогом библиотеки с **внешним API**.
  *   **Внешнее API = Список Actions**, которые компонент готов выполнить. Это позволяет тестировать компоненты как «черные ящики»: мы подаем Письмо на вход и проверяем результат через Шину или State, не обращаясь к внутренним приватным методам.
- **Децентрализация**: Нет «Божественного объекта», который знает всё обо всех. Каждая сущность автономна.
- **Читаемость как приоритет**: Код должен читаться как текст.

## 📂 2. Анатомия Книги (Оглавление)

Каждая Книга (модуль) имеет строгую внутреннюю структуру, имитирующую разделы печатного издания:

### 📚 `introduction` (Введение — Техническая обвязка)
Здесь сосредоточена вся «физика» и инструменты, необходимые для существования Книги. Всё разложено по тематическим «полкам»:
- **`rules/`**: Переиспользуемые правила мира (`Rule_HttpGet`, `Rule_ValidateEmail`). Это атомарные функции, выполняющие тяжелую или общую работу.
- **`screens/`**: Визуальный ряд. Содержит подпапки по названиям экранов (например, `profile/`). В каждой подпапке лежат файлы **Screen** (тело) и **State** (память).
- **Фундамент**: Базовые классы, такие как `Bus.kt` (Шина), `StateScreenClass.kt` и системные регистраторы.

### 📖 `chapters` (Главы — Сюжетные линии)
Логический центр принятия решений. Разделен на подпапки по названиям сюжетов.
- **Глава (Chapter)** — это координатор событий. Она получает письма из Шины и решает, какой сюжетный поворот запустить.
- **Спящий режим**: Глава живет в памяти только тогда, когда активен её сюжет.

### 🔗 `adapters` (Адаптеры — Заметки на полях)
Раздел для интеграции с внешним миром и Legacy-кодом:
- Содержит файлы **Адаптеров** и старый код, который еще не переведен на язык Книги.
- Адаптер переводит внешние сигналы в Письма для Шины, позволяя Книге расти внутри старого проекта без его полной переработки.

## ⚙️ 3. Ключевые механизмы (Магия методологии)

### 🚌 Шина (Bus): Нервная система Книги
Шина — это не просто посредник, а интеллектуальный диспетчер:
- **Реестр живых объектов**: Хранит все активные Главы и Состояния. Позволяет любому Правилу найти нужный `State` мгновенно.
- **Динамическое рождение**: Если вы отправляете письмо Главе, которой еще нет в памяти, Шина **сама создаст её**.
- **Потокобезопасность**: Использование конкурентных коллекций (`ConcurrentHashMap`) гарантирует стабильность при асинхронной работе.

### ✉️ Письма (Letters) и исполнение сюжета
Связь между компонентами идет через объект `Letter`. 
- **Глава САМА выполняет метод**: Когда письмо доходит до адресата, Шина вызывает её метод `invoke(letter)`. 
- **Отсутствие посредников**: Глава получает письмо и сама решает, как на него реагировать через внутреннюю логику (`when(action)`). 
- **Поле `from`**: Каждое письмо подписано, что обеспечивает полную трассируемость событий.

### ⚡ Short Circuit (Короткий путь данных)
В CoB путь данных сокращен: **`Rule -> State -> Screen`**.
- Глава инициирует процесс: «Мир, дай мне погоду!».
- Правило выполняется асинхронно и **напрямую пишет результат в State**.
- Экран мгновенно реагирует на изменение. Глава освобождена от рутины «почтового голубья».

### 🛡️ Трассируемость (ID == Class == File)
Мы решаем проблему «невидимых связей» через жесткое соглашение:
- ID объекта в Шине всегда совпадает с именем его Класса и Файла.
- Лог Шины (`BusLog`) — это готовая стенограмма работы приложения.
- Это дает мгновенную навигацию через `Double Shift` по любому ID из лога.

## 🚀 4. Сравнение прочности (Стресс-тест)

| Критерий | Clean Architecture | **Code of Book (CoB)** |
| :--- | :--- | :--- |
| **Скорость фичи** | Медленно (много слоев) | **Мгновенно** (Rule -> State) |
| **Поиск бага** | Квест по файлам и интерфейсам | **Чтение лога** (Кто, Кому, Что) |
| **Память** | Забита DI-синглтонами | **Идеально** (TTL и спящие Главы) |
| **Порог входа** | Недели на изучение слоев | **Часы** на понимание сюжета |

## 💡 Итог

Методология **«Код как Книга»** — это выбор для тех, кто хочет **создавать продукт**, а не обслуживать его архитектурный скелет. Мы убираем инфраструктурный шум, оставляя только Сюжет и Физику.
