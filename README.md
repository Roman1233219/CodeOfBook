# 📖 Code as Book (CoB) Methodology

> **Превращаем разработку ПО из проектирования «заводов-монолитов» в написание живой, читаемой и автономной истории.**

**Code as Book (CoB)** — это децентрализованная архитектурная парадигма, созданная для типовых бизнес-приложений. Она заменяет горизонтальное слоение классических архитектур на вертикальное деление по смыслу, делая код понятным как оглавление книги.

---

## 🚀 Фундаментальная философия: Смерть «Архитектурного Налога»

В таких архитектурах, как Clean или Hexagonal, логика размазана горизонтально (`Data -> Domain -> Presentation`). Чтобы добавить одну кнопку, разработчику часто приходится «протыкать» 5–7 слоев, тратя до **40% времени** на обслуживание структуры, а не на бизнес-логику.

**CoB меняет правила игры:**
*   🏛 **Приложение — это Библиотека.** Проект состоит из независимых **Книг** (модулей).
*   📘 **Книга — это автономный мир.** У неё есть своя память (**Сущности**), свои глаза (**Экраны**) и своя воля (**Главы**).
*   ✍️ **Читаемость — приоритет №1.** Если сюжет приложения нельзя прочитать как текст, это плохой код.

---

## 📂 Анатомия Книги (Оглавление)

Каждая Книга имеет строгую структуру папок, обеспечивающую изоляцию и порядок:

### 📚 ВВЕДЕНИЕ (Introduction — Физика Мира)
Инструменты, без которых мир не существует:
*   **СУЩНОСТИ (Entities):** Описание памяти. Состояние приложения, которое напрямую связано с отображением.
*   **ЭКРАНЫ (Screens):** Визуальный ряд (например, Jetpack Compose). *Только декларативный UI, никакой логики.*
*   **ПРАВИЛА (Rules):** Законы физики. Атомарные процедуры: запросы, валидация, сохранение данных.
*   **ПОДКЛЮЧИТЬ (Imports):** Реестр внешних библиотек и шаблонов.

### 📖 ГЛАВЫ (Chapters — Сюжетные линии)
Логический центр принятия решений. 
*   **Глава — это Режиссер.** Она говорит, *что* происходит, но не знает, *как* это устроено технически.

### 🔗 ЗАМЕТКИ (Adapters — Заметки на полях)
Шлюзы для связи с внешним миром: Legacy-код, GPS, Bluetooth, сторонние API. Единственное место, где допускается взаимодействие с «грязным» платформенным кодом.

---

## 🧠 Нервная система: Шина и Письма

Все компоненты общаются исключительно через **Письма (Letters)**, которые доставляет **Шина (Bus)**.

### Структура Письма (`PlotSignal`)
| Поле | Описание | Пример |
| :--- | :--- | :--- |
| **ОТПРАВИТЕЛЬ** | Кто породил событие | `BOOK.SCREEN.BUTTON` |
| **ПОЛУЧАТЕЛЬ** | Кому адресовано | `CHAPTER_AUTH` или `RULE_NETWORK` |
| **МЕТОД** | Что произошло | `CLICK`, `SUCCESS`, `ERROR` |
| **ДАННЫЕ** | Параметры события | `JSON / Map` |

> 💡 **Принцип Traceability:** `ID объекта == Имя Класса == Имя Файла`.  
> Лог Шины становится готовой стенограммой работы приложения, понятной даже бизнес-заказчику.

---

## 🎬 Логика Сюжета: Закон Успеха (Happy Path)

**Глава — это «Хроника Побед».** В ней строго запрещены ветвления по ошибкам.

1.  **Декларативность:** Глава состоит только из триггеров: `Событие -> Реакция`.
2.  **Слепая Вера:** Глава реагирует только на сигнал **УСПЕХ** от Правила. Если Правило споткнулось, Глава просто «замирает», не загромождая сюжет техническим мусором (404, Timeout и т.д.).
3.  **Цепочки:** Глава связывает выход одного Правила со входом другого, создавая непрерывную сюжетную линию.

---

## ⚙️ Физика Действия: Автономия Правила

**Правило — это Ответственный Исполнитель (Каскадер).** Оно берет на себя всю «грязную работу» и риски.

### Архитектурный Контракт Правила
Каждое Правило обязано иметь три блока:

1.  **ДЕЙСТВИЯ:** Линейный конвейер команд (Установить, Запросить, Сохранить).
2.  **ОШИБКА (Обязательно):** План спасения. Если любая команда упала, Правило само вызывает обработчик (показывает Toast, логирует ошибку) и **не беспокоит Главу**.
3.  **УСПЕХ (Автоматически):** Если конвейер дошел до конца, Шина отправляет письмо в Главу.

> 📁 **Вертикальное деление:** Для каждой Главы создается своя подпапка в ПРАВИЛАХ. Это изолирует уникальную логику сюжета от общих законов мира.

## ⚡ Механизмы исполнения

### Short Circuit (Короткий путь данных)
Данные не гоняются через Главу обратно в UI.
1.  Глава вызывает Правило.
2.  Правило пишет результат **напрямую в СОСТОЯНИЕ (State)**.
3.  Экран (UI) мгновенно перерисовывается, так как он слушает State.
4.  Глава получает лишь короткий отчет: «Готово».

### 🔗 Адаптеры (Двусторонние Шлюзы)
Адаптер — единственный объект, имеющий право касаться «грязного» Android-кода. Он переводит внешние сигналы в Письма и обратно, оставляя Книгу стерильной.

---

## 🎯 Резюме

В методологии CoB разработчик перестает быть «механиком», который возится в масле инфраструктуры. Он становится **Автором**.

*   🖋 **Пиши Главу как поэт** (о смысле и сюжете).
*   ⚖️ **Пиши Правило как юрист** (о деталях, рисках и контрактах).
*   📖 **Пусть Книга работает сама.**

Этот подход сокращает **Time-to-Market** в разы, делая поддержку приложения такой же простой, как чтение оглавления.
